## 一、实验目的

1. 了解网络空间搜索引擎的工作原理，能说清它与普通搜索引擎的区别

3. 能用至少三种方法完成目标域名的子域名收集

## 三、什么是网络空间搜索引擎

普通搜索引擎（百度、Google）爬取的是**网页里的文字内容**，回答"上哪能查到某个资料"；
网络空间搜索引擎（ZoomEye、FOFA、Shodan）扫描的是**互联网上的设备和端口**，回答"公网上有多少台设备开着某个服务"。

一句话区别：**普通搜索引擎搜索信息，网络空间搜索引擎搜索资产。**

它的工作过程可以理解成三步：

1. 对公网 IP 段发起扫描，探测开放的端口
2. 与端口建立连接，抓取返回的 banner / 网页内容
3. 与指纹库比对，识别出这是什么组件、什么版本，然后建索引

## 五、ZoomEye 实战

### 5.1 常用搜索语法

| 字段 | 含义 | 示例 |
|------|------|------|
| `app:` | 组件 / 产品名 | `app:"Apache"` |
| `os:` | 操作系统 | `os:Linux` |
| `title:` | 网页标题 | `title:"后台管理"` |
| `port:` / `service:` | 端口 / 服务 | `port:8080`、`service:ssh` |
| `country:` / `city:` | 国家 / 城市 | `country:CN` |
| `ip:` | IP 或网段 | `ip:202.193.64.0/24` |
| `hostname:` / `site:` | 域名 | `hostname:guet.edu.cn` |

### 5.2 搜索一：按组件检索

- 语法：`app = "nginx" && country = "CN"`
- 历史累计命中：102,931,532 条
- 近一年数据：30,607,659 条
- 查询耗时：3.510 秒

ZoomEye 同时给出了「历史累计」与「最近一年」两个数字，二者相差约 3.4 倍。
这说明测绘引擎本质上是一个持续更新的**快照库**，而非实时监视器：库中约三分之
二的记录在近一年内未被再次观测到，可能已下线、变更 IP 或完成升级修复。因此
在做资产梳理时，应以「最近一年」的数据衡量当前暴露面，直接使用累计总量会显
著高估实际情况。

从单条结果看，目标返回 `302 Moved Temporarily` 并携带 `Location` 跳转至
HTTPS 地址，同时设置了 `Strict-Transport-Security`，说明其已强制启用 HTTPS
并配置了 HSTS。其 `Server` 字段仅返回 `nginx` 而未暴露具体版本号，推测已关闭
`server_tokens`，这在一定程度上提高了攻击者定位已知漏洞的门槛——但测绘引擎
仍能通过其他指纹识别出组件类型，说明隐藏版本号只能提高成本，无法真正隐匿。

另外，命中的主机名中包含 `test` 字样，属于典型的测试环境遗留资产。此类系统
通常缺少正式的补丁维护与访问控制，在实际攻防中是优先关注的对象。

![按组件检索结果](/img/zoomeye-nginx.png)

### 5.3 搜索二：按端口 / 服务检索

- 语法：`port = "6379" && country = "CN"`
- 历史累计命中：1,637,018 条
- 近一年数据：478,657 条
- 查询耗时：0.178 秒

6379 是 Redis 的默认端口。国内近一年约有 47.8 万台主机的 Redis 端口处于
公网可达状态。累计数据与近一年数据同样相差约 3.4 倍，与上文 nginx 的检索结果
呈现出一致的比例关系，进一步印证了测绘引擎「快照库」的特性。

> **一个值得记录的踩坑过程**：初次检索时使用 `"port:6379"`（整体加引号）的
> 写法，返回结果均为 80 端口的 Web 站点，命中数虚高至 50 余万。原因是加引号后
> 该字符串被当作全文关键词匹配，而非字段筛选。**验证方法**是查看结果卡片的端口
> 标签与服务标签——修正为 `port = "6379"` 后，标签分别显示 `6379` 与 `redis`，
> 命中数回落至合理区间。这一过程说明使用测绘引擎时必须核对返回结果的字段一致性，
> 不能仅凭总数量下结论。

![错误写法：命中结果端口为 80，服务为 nginx](/img/zoomeye-redis-wrong.png)

从单条结果看，该主机 Banner 返回 `-NOAUTH Authentication required`，表明连接
已建立但要求身份认证，即该实例已启用密码保护。作为对比，若 Banner 直接返回
`+PONG` 或版本信息，则说明实例未设置认证，任何人皆可读写其中的数据，即典型的
Redis 未授权访问情形。

需要指出的是，启用认证并不等同于安全：Redis 的 AUTH 机制为明文传输，且实际
部署中弱口令比例较高，在网络可达的前提下认证仅提高攻击成本。规范做法是让 Redis
仅监听回环地址或内网接口，从网络层禁止外部访问，而非依赖认证兜底。本例中该主机
隶属于公有云（AS38283），云平台安全组默认策略为拒绝所有入站，说明该端口规则
系使用者主动放开，问题根源在于配置习惯。

![Redis 端口暴露情况](/img/zoomeye-redis.png)

### 5.4 搜索三：针对目标域名检索

- 语法：`domain = "guet.edu.cn"`
- 历史累计命中：214 条
- 近一年数据：213 条
- 查询耗时：0.865 秒

与前述通用检索相比，本组数据的数量级差异显著：全网口径下的 Redis 暴露主机达
47.8 万台，而一个组织对外暴露的 Web 资产仅两百余条。这一对比说明单一组织的
资产边界是有限且相对固定的，正因如此，资产梳理与暴露面收敛才具备可行性。

此外，本例累计数据与近一年数据几乎一致（214 对 213），与前述 nginx、Redis 两组
相差 3.4 倍的情况截然不同。原因在于，大范围通用检索中包含大量已下线、变更地址
的陈旧记录，而组织内部系统一旦上线便长期在线，变动很小。这一现象反向印证了前述
方法论：当累计与近期数据接近时，说明资产稳定、数据可靠；二者相差悬殊时，则需
警惕陈旧记录对分析结论的干扰。

从响应头看，目标返回 `200 OK` 但 `Server` 字段为空，即服务器未返回该字段。
结合前两组结果，可归纳出信息隐藏的三个层级：

| 配置状态 | 典型响应 | 说明 |
|----------|----------|------|
| 默认 | `Server: nginx/1.18.0` | 软件与版本全部暴露 |
| 隐藏版本 | `Server: nginx` | 版本已隐藏，软件类型仍可识别 |
| 完全隐藏 | 无 `Server` 字段 | 需借助其他指纹推断 |

本例属于第三种，通常由反向代理回源重写响应头，或直接剔除该响应头实现，属于
较为彻底的加固措施。

此外，检索结果中出现 `oa.guet.edu.cn`，其服务运行于 80 端口，即 OA 系统以明文
HTTP 方式对外提供服务。OA 承载的是内部办公与审批数据，通过明文协议传输存在
被旁路嗅探的风险。此处仅记录观测到的端口与协议状态，未对系统进行登录尝试或
漏洞测试，建议相关单位核查是否已对全部入口强制跳转 HTTPS。

**结果差异的原因：** 各平台的扫描周期、探测深度、入库规则、覆盖区域（国内/国外比重）都不相同，因此同一目标在不同引擎上的命中数量必然存在出入，不能简单地认为某个平台"更准确"。实际做资产梳理时通常**多个引擎交叉验证**，取并集。

## 七、子域名收集

### 7.1 为什么先收子域名

主域名通常是门户官网，防护最完善；而 OA、测试环境、运维后台这些往往挂在子域名上，防护弱、版本旧，是更现实的入口。所以攻击面侦查第一步基本都是子域名收集。

### 7.2 方法一：搜索引擎语法

- 必应 / 百度：`site:guet.edu.cn`、`site:guet.edu.cn -site:www.guet.edu.cn`
- FOFA：`domain="guet.edu.cn"`
- ZoomEye：`hostname:guet.edu.cn`

<!-- ![搜索引擎语法收集子域名](/img/subdomain-search.png) -->

### 7.3 方法二：证书透明度日志（CT Log）

HTTPS 证书的签发记录是公开可查的，证书里会写明覆盖的子域名，因此可以顺着证书反向找回子域名。

- crt.sh：https://crt.sh ，搜索 `%25.guet.edu.cn`
- Censys：`names: guet.edu.cn` 或 `parsed.names: guet.edu.cn`

> 注意：crt.sh 偶尔会返回 502/超时，属于该站常态，多刷新几次或改用 Censys 即可。

<!-- ![证书透明度日志查询结果](/img/subdomain-crtsh.png) -->

### 7.4 方法三：DNS 数据聚合（免注册，效果最好）

以下站点直接使用浏览器访问即可：

- https://api.hackertarget.com/hostsearch/?q=guet.edu.cn （直接返回「域名,IP」纯文本）
- https://dnsdumpster.com （附带一张资产拓扑图）
- https://searchdns.netcraft.com
- https://rapiddns.io/subdomain/guet.edu.cn

<!-- ![DNS 聚合站点查询结果](/img/subdomain-dns.png) -->

### 7.5 结果汇总与分析

各渠道结果合并去重后，共得到子域名 **44** 个。

<!-- 下面这行命令可以贴成代码块，说明是怎么拿到数据的 -->
```text
https://api.hackertarget.com/hostsearch/?q=guet.edu.cn
```

| 指标 | 结果 |
|------|------|
| 子域名总数 | 44 |
| 去重后独立 IP | 4 |
| 出现最多的 IP | `202.193.64.75`（承载 41 个子域名） |

**关键发现：**

41 个子域名同时解析到同一个 IP `202.193.64.75`，这种现象说明域名前方存在**统一的入口设备**（反向代理 / CDN / WAF），真实业务服务器的 IP 被隐藏在后方。这样做有两个好处：一是收敛对外暴露面，二是对外只暴露一个高防节点，安全性和运维复杂度都可控。

从资产类型看，收集到的子域名包含：

- 教学资源类：`courses`、`classroom`、`jpkc`、`itest`
- 管理/服务类：`portal`、`idp`、`sitemanage`、`mainweb`
- 专项业务：`zsb`（招生）、`dag`（档案）、`opac`（图书馆书目）、`wvpn`（Web VPN）
- 测试类：`bkjwtest`、`exp`、`itest` ← **测试系统往往是防护最薄弱的一环**

## 八、结论

1. 网络空间搜索引擎把"资产发现"的成本降到了极低：**任何联网设备只要对外开放端口，都会被动暴露信息**，运维人员无法通过"不被发现"来保证安全。
2. 多引擎交叉查询是必要的，单一引擎的数据都存在盲区。
3. 子域名+端口+组件版本三者组合，基本可以还原出一个组织对外的完整攻击面。
4. 对应的防护建议：
   - 非必要端口不对外开放，数据库、缓存服务一律不监听公网
   - 管理后台、测试系统不要挂公网，加白名单或 VPN 访问
   - 及时更新组件版本，避免长期运行存在公开漏洞的旧版本组件
   - 使用 CDN / 反向代理隐藏源站 IP
   - 定期用这些引擎自查本单位资产，把发现前移到发现之前
